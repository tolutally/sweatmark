# SweatMark security, reliability, and product review

Reviewed commit `0093a8b` on 2026-10-24. Repository downloaded into the existing empty Git workspace. This is a source review, not a live penetration test or a visual usability test. No production endpoints were exercised and no credentials were used. Application source remains unchanged.

## Assessment

There is a useful workout-logger foundation here, but it is not ready for a trustworthy release. The priority is credential containment and reliable, account-isolated workout storage. More features or visual polish will not compensate for missing notes, mislabelled weights, disappearing history, or unjustifiably precise recovery scores.

## Findings, in priority order

### 1. Critical: committed credentials and source-visible admin passwords

Evidence: `AuthKey_9P27Z4DS2F.p8:1`; `functions/src/index.ts:341`, `:1426`, `:1432`, `:1628`, `:1684`, `:1690`.

The Apple file parses as a private key with OpenSSL. GymFit handlers contain a literal RapidAPI credential. Several bulk import/refresh handlers accept a shared password embedded in this same repository, including through URL query parameters. Anyone with repository access has these values; if the handlers are deployed and reachable, their application-level password is no meaningful barrier. Actual key validity, Apple permissions, deployment, and IAM exposure were not checked.

Revoke/rotate the exposed credentials first, replace shared-password checks with verified admin authorization, then remove secrets from tracked files and coordinate history cleanup. Put replacement API credentials in the existing Secret Manager pattern. Add secret scanning and ignore private-key files. Do not mistake ordinary Firebase client configuration or the distribution certificate for equivalent private credentials. The existing `audit.md` already flags the Apple key; the key remains tracked.

### 2. High: ordinary callers can cause paid backend work

Evidence: `functions/src/index.ts:66`, `:212`, `:453`, `:607`, `:1613`.

Search, exercise lookup, and image refresh do not require authentication. Full download callables require only a signed-in user, not an admin. There is no App Check enforcement or per-user rate limit in these handlers. Search's Firestore limit also takes client input without a validated bound before the API-side clamp. Repeated misses/refreshes can consume upstream quota and database writes; a normal account can start bulk imports.

Require admin claims for imports, validate types/lengths/limits, protect public-facing calls with appropriate authentication/App Check and quotas, and make bulk operations single-flight jobs. App Check alone is not admin authorization. Verify deployed IAM separately.

### 3. High: local data and active workouts are not isolated by account

Evidence: `lib/services/storage_service.dart:10`; `lib/state/workout_notifier.dart:61`; `lib/main.dart:190`; `lib/services/recovery_service.dart:221`.

Workouts, drafts, custom exercises, and recovery use device-wide filenames. The workout notifier restores history and a draft before account-specific loading. Logout clears the profile but does not reset the active workout, its draft, or those files. A user can log out with a draft and the next account can inherit it, potentially saving it to that account. A cloud response for an earlier account can also finish after an account switch without a UID/generation guard.

Scope storage and state by UID, reset all session-owned state on logout, cancel or reject stale asynchronous results, and define an explicit guest-data migration policy. Verify with two test accounts and with offline switching.

### 4. High: cloud failures hide history and offline sync is not durable

Evidence: `lib/services/firebase_service.dart:370`, `:402`; `lib/services/sync_service.dart:27`, `:108`; `lib/main.dart:196`; `lib/state/workout_notifier.dart:568`.

Firebase reads catch errors and return `[]`, so SyncService's exception-based local fallback never runs for those failures. Even a successful cloud read does not merge pending local workouts. Failed saves are retried only three times in an in-memory queue. The migration helper has no caller. Cloud history is not written into the local file, and finishing a workout reloads that local file; on another device this can replace displayed cloud history with only locally logged sessions. The real-time listener callback merely prints a message.

Use a per-user persistent outbox, explicit error states, ID-based merge/upsert, and durable deletion tombstones. Treat local storage as a coherent cache rather than a disconnected second database. Show whether a workout is saved locally, pending, synced, or failed. Test restart while pending, exhausted retries, second-device history, and offline deletion.

### 5. High: units relabel numbers without converting them

Evidence: `lib/models/user_settings.dart:40`, `:47`; `lib/models/workout_model.dart:3`; `lib/screens/active_workout_screen.dart:2313`, `:2343`.

Input stores raw numeric weight and the set model has no unit. Formatting appends the currently selected unit without conversion. Changing pounds to kilograms can turn the same stored 100 into “100 kg.” Distance has the same storage ambiguity. PR, volume, and recovery calculations cannot reliably compare mixed-unit entries. Dynamic input suffix selection also derives from the weight-unit preference, despite a separate distance preference.

Choose canonical storage units, convert on entry/display, and record enough metadata to migrate existing values safely. Do not silently infer historical units when they are unknown. Verify that 100 lb and its kg equivalent produce the same volume and record comparisons.

### 6. High: saving and restoring loses user-entered data

Evidence: `lib/state/workout_notifier.dart:81`, `:138`, `:456`, `:531`, `:801`; `lib/screens/workout_summary_screen.dart:516`.

Draft serialization/restoration only preserves weight, reps, and completion for each set; duration, distance, speed, incline, resistance, and rest metadata are omitted. Both finish paths rebuild WorkoutLog without notes or the top-level superSets list. The summary passes notes to `finishWorkoutWithData`, but that argument is ignored. Editing history notes rewrites local history, then calls `syncWorkout(null, ...)`, which appends another local copy and performs no cloud update.

Reuse complete model serialization and copy methods. Update by stable ID, preserve every field, and use the authenticated user for cloud updates. Verify cardio draft round trips, completed-workout notes and supersets, and note edits across restart and a second device.

### 7. High: legacy recovery migration can recurse indefinitely

Evidence: `lib/services/recovery_service.dart:226`, `:248`, `:272`, `:308`.

Reading an old-format local recovery file calls migration. Migration calls the local save method, which reads the same unmigrated file again before writing. That re-enters migration indefinitely. Existing users with `lastTrainedDate` data can get a hanging read/save path.

Separate raw file reads/writes from migration, migrate once in memory, and atomically replace the file. Verify with an old-schema fixture and a second read after migration.

### 8. Medium: Firestore permits ownership reassignment and client-written streak totals

Evidence: `firestore.rules:59`, `:119`, `:133`; `functions/src/index.ts:1167`.

Template and collection updates verify the existing owner but do not require the resulting owner to remain the same. A user can transfer their own document into another user's namespace/queries by setting userId to the victim UID. This is an integrity/injection issue, not proof of reading arbitrary victim documents. Streak documents are fully client-writable even though the backend uses their counters to award milestones.

Keep ownership immutable and validate allowed fields. Separate editable streak preferences from server-owned counters/achievements. Add rules tests for owner, non-owner, anonymous, owner-change, malformed fields, and derived-field writes. The existing per-user owner checks and default deny are useful protections; this is not an openly readable database.

### 9. Medium: recovery UI promises more certainty than the implementation supports

Evidence: `lib/services/recovery_service.dart:29`, `:100`, `:180`; `lib/screens/recovery_screen.dart:107`, `:557`; `lib/screens/muscle_detail_screen.dart:199`, `:403`.

Readiness comes from fixed strain formulas, fixed decay constants, and a 1.3 multiplier. Three completed sets of 10 at stored weight 50 produce 150 strain points, immediately clamped to 100 fatigue. Many substantially different sessions therefore produce the same score. Unknown/untracked muscles start green. The UI shows exact percentages and “Until Ready”; no validation/calibration evidence was found in the repository. Its projection caveat explains the formula's assumption, not the uncertainty of the score.

Present this as an estimated training-load/recovery indicator, distinguish unknown from recovered, explain inputs and limitations, and add user feedback such as soreness and perceived effort. This is a product-evidence concern, not a medical assessment of the formula.

### 10. Medium: notifications have missing end-to-end plumbing

Evidence: `lib/services/notification_service.dart:200`, `:206`, `:233`; `functions/src/index.ts:1371`.

The client fetches/logs FCM tokens but has no token upload implementation; the reminder job expects a token at `users/{uid}/profile/data.fcmToken`. Notification navigation remains TODO. Reminders have no complete client-to-server path in this source. Register tokens per account/device, refresh and remove them appropriately, stop logging tokens, and implement notification routing. Verify foreground, background, terminated, and account-switch behavior.

### 11. Medium: release verification is insufficient

Evidence: `test/widget_test.dart:15`; `android/app/build.gradle.kts:38`; `pubspec.yaml`; tracked test files.

The smoke test builds only a “0” text widget, then tries tapping a nonexistent plus icon and expects “1”; it does not exercise SweatMark and is structurally broken. The other two tracked Dart tests focus on profile behavior/model data. No tracked CI workflow was found. Android release explicitly uses debug signing. The 4,072-line active workout screen and 925-line workout notifier make it hard to isolate and verify critical state transitions.

Replace the dummy test, add meaningful save/restore/account-switch/unit/rules coverage, establish CI, and configure production Android signing. Split persistence and workout state transitions out of UI code before adding more functionality.

## Why the product can feel unconvincing

- A workout logger's promise is remembering exactly what the user did. Dropped notes, ambiguous units, and inconsistent history directly break that promise.
- Exact-looking recovery percentages and countdowns create apparent authority unsupported by validation in this repository. Unknown data should not look like a positive measurement.
- AI coaching is only an empty service (`lib/services/ai_coach_service.dart`). The README correctly places it on the roadmap; do not market it as available.
- The repository describes an ultra-modern dark design, while substantial screens use light surfaces; its roadmap still lists already-present Firebase, templates, and analytics as future work. Documentation does not provide a reliable account of the product.
- No account-deletion flow or privacy/terms UI was found in the inspected Dart source. For an account-based fitness product, users need understandable data controls and a way to leave. This is a product gap, not a legal compliance determination.
- The code has more feature breadth than verification depth. Prioritize a fast, dependable start → log → finish → revisit loop before adding social or AI features.

## Recommended execution order

1. Contain credentials and restrict privileged backend operations. Confirm deployed IAM/rules separately.
2. Fix per-account storage, canonical units, complete serialization, durable sync, and the migration recursion.
3. Add regression tests for those exact failures and a release CI gate.
4. Reword recovery estimates and unknown states; complete notifications and data controls.
5. Run the app on devices and review logging speed, keyboard/focus behavior, accessibility, empty/error states, and visual consistency. No visual judgement should be considered verified by this source-only review.
